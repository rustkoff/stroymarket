# ПР 3: пояснения для защиты

Показать каталог, товар, регистрацию, корзину и заказ. Затем открыть тот же заказ из второго аккаунта: сервер отвечает 404. JSON-каталог находится в `/api/products`, документация — `/docs`.

1. **Почему SQLite:** один файл, нет отдельной службы; для учебного магазина достаточно. `app/schema.sql` задаёт PK, FK и ограничения количества/цены. `PRAGMA foreign_keys=ON` выполняется на каждом соединении.
2. **Модель:** users — аккаунты, products — 15 товаров, cart_items связывает пользователя с товаром. Один пользователь имеет много orders; order_items хранит состав каждого заказа. sessions и feedback — вспомогательные сущности. Цена и название копируются в заказ, чтобы история не зависела от будущего изменения каталога.
3. **Как данные доходят до браузера:** FastAPI выбирает строки SQLite, передаёт их Jinja2, шаблон формирует HTML. Это собственный сервер, а не чтение JSON-файла в браузере. `/api/products` показывает те же строки в JSON. Начальный `products.json` нужен только для наполнения отсутствующих записей при запуске.
4. **Параметризованный запрос:** `db.execute('SELECT * FROM orders WHERE id=? AND user_id=?', (order_id, user_id))`. SQL и значения передаются отдельно. Проверка владельца находится в запросе, а не в скрытии кнопки.
5. **Хеширование:** `PasswordHasher.hash` из argon2-cffi создаёт Argon2id со случайной солью. `verify` проверяет пароль без возможности получить его из хеша. SHA-256 применяется только к случайным токенам, пароли им не хешируются.
6. **Сессия:** случайная cookie → SHA-256 токена → строка sessions → user_id. Cookie HttpOnly, SameSite=Lax, на HTTPS Secure. База сессий переживает пересоздание контейнера. Вход и выход заменяют токен; выход удаляет старую сессию. Срок входа 7 дней.
7. **CSRF:** каждая форма передаёт случайный токен, связанный с текущей серверной сессией. Сервер проверяет его, Origin и Sec-Fetch-Site. Это защищает от отправки действия посторонним сайтом с cookie пользователя. Без входа действия корзины, заказа и обратной связи отклоняются.
8. **Транзакция:** заказ создаётся под `BEGIN IMMEDIATE`, копирует корзину и очищает её атомарно. Если возникает исключение, sqlite3 откатывает транзакцию. Повторный POST получает пустую корзину, второй заказ не создаётся.
9. **Проверки:** ограничения длины FastAPI + проверка имени/email/пароля; количество 1…10000, для удаления 0; лимит тела 16 КиБ, попыток входа и параллельного Argon2. Ошибка не возвращает пароль в ответе.
10. **Обратная связь:** frontend проверяет поля рядом с вводом, после успеха выполняется настоящий POST. Вошедшее сообщение сохраняется в SQLite, email не отправляется — это видно в результате.

Разобрать `app/db.py`, затем обработчики `register`, `login`, `create_order`, `owned_order` в `app/main.py`. В браузере показать Network: HTML от своего сервера, `/api/products`, внешний `daily_json.js`; источник курсов не связан с хранением заказов.

ПР 1–2 в отчёте описывают предыдущие состояния. Пояснения тех этапов не означают, что корзина сейчас статическая. Микросервисов и ORM нет, frontend остался обычным JavaScript.
