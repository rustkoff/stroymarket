# Памятка к защите: «СтройМаркет», вариант 14

Памятка помогает объяснить проект своими словами. Сверьте её с текущим кодом перед защитой: описывать как сделанное можно только то, что действительно реализовано и проверено.

## Коротко о проекте

Это учебный каталог строительных материалов. Сценарий варианта 14 — подобрать материал и рассчитать необходимое количество по площади или объёму. Интерфейс включает главную, каталог, карточку товара, калькулятор, корзину, контакты и аккаунт. Каталог и корзина связаны с сервером; аккаунт нужен для персональных данных корзины. Цены хранятся в базовой валюте; внешний курс ЦБ РФ можно использовать для дополнительного пересчёта отображения.

## Как объяснить основные части

- **HTML** задаёт структуру и смысл: `header`, `nav`, `main`, `section`/`article`, `footer`, формы и кнопки. CSS отвечает за внешний вид, а не за смысл документа. На странице один `h1`, а уровни подзаголовков идут последовательно.
- **Адаптивность и доступность:** Grid/Flexbox помогают перестраивать каталог и блоки; media queries меняют компоновку на узком экране. `alt` описывает содержательное изображение, управление с клавиатуры и видимый фокус помогают тем, кто не пользуется мышью.
- **JavaScript:** читает ввод, проверяет форму, обновляет DOM без перезагрузки. `fetch` возвращает Promise; интерфейсу нужны состояния ожидания, успешного ответа и ошибки. При недоступности внешнего API надо сообщить об этом и оставить основную страницу пригодной к использованию.
- **Калькулятор:** сначала привести ввод к согласованным единицам. Для покрытия площадью `C` на единицу материала и площади `A` базовое количество `Q = A / C`; при доле запаса `r` — `Q = A × (1 + r) / C`. Если товар продаётся упаковками с выходом `P`, упаковки `N = ceil(Q / P)`. Для объёма аналогично использовать `Q = V / yield`. Единицы и правила расхода должны соответствовать конкретному товару; это расчётная оценка, а не гарантия фактического расхода.
- **FastAPI и SQLite:** FastAPI принимает HTTP-запросы и возвращает ответы, SQLite хранит реляционные данные. Таблицы товара, пользователя и позиции корзины связаны идентификаторами. Сервер валидирует запрос и проверяет, кому принадлежит корзина.
- **Аутентификация и безопасность:** пароль не хранится открытым текстом — сохраняется хеш через проверенную библиотеку. При входе проверяется пароль по хешу. Параметризованный SQL отделяет значения от текста запроса; нельзя составлять SQL конкатенацией пользовательского ввода. Скрытая кнопка не заменяет серверную проверку прав.
- **HTTP, Docker, HTTPS:** браузер отправляет запрос серверу по HTTP(S); HTTPS защищает соединение TLS. Docker упаковывает приложение и зависимости для воспроизводимого запуска, но сам по себе не означает, что сервис опубликован или защищён HTTPS.

## Что уметь показать по коду

Подготовьтесь найти общий шаблон/меню и стили, обработчик фильтра или расчёта, запрос `fetch`, обработчик API товара/корзины, модель таблиц, проверку пароля и параметризованный запрос. Будьте готовы объяснить один путь данных целиком: действие пользователя → запрос браузера → серверная проверка → SQLite → ответ → обновление интерфейса. На защите показывайте актуальный код и фактическое поведение, а не только этот документ.

## Вопросы для самопроверки

1. Почему каталог — не только набор карточек? Он позволяет найти товар по категории/характеристикам и перейти к подробностям.
2. Что происходит при сетевой ошибке валютного API? Как минимум показывается понятное сообщение, а каталог и расчёт по базовой цене остаются работоспособными.
3. Чем хеширование отличается от шифрования? Хеш предназначен для односторонней проверки пароля; исходный пароль не должен восстанавливаться из базы.
4. Почему проверять принадлежность корзины только в браузере недостаточно? Клиент контролируется пользователем; сервер должен сам определить текущего пользователя и запретить доступ к чужим данным.
5. Как проверить адаптивность? Посмотреть каждую страницу на ширине 360 px, убедиться в отсутствии горизонтальной прокрутки и доступности меню/форм.
6. Что доказывает HTTPS и что он не доказывает? HTTPS подтверждает защищённое соединение с доменом, но не корректность расчётов, хранение данных или полноту приложения.

Не заявляйте, что выполняли развёртывание, тесты или получили конкретные результаты, пока это не подтверждено реальными действиями и проверяемыми свидетельствами.
